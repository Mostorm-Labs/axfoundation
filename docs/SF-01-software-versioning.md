# SF-01 — 软件版本管理规范

- **状态：** 提案中
- **版本：** 1.0
- **负责人：** 软件工程
- **关联规范：** SF-04、SF-05、SF-07、SF-10

## 1. 目的

建立简单、统一且可追溯的软件版本规则。产品、固件、更新器和 SDK/API 使用统一的版本表示方式；通信协议和持久化数据格式等具有独立兼容周期的契约，仍单独管理。

## 2. 版本维度

| 维度 | 示例 | 变更时机 |
|---|---|---|
| 软件版本 | `2.4.1_1024` | 产品/组件版本及其构建发生变化 |
| 协议版本 | `1.3` | 通信协议契约发生变化 |
| 数据/Schema 版本 | `5` | 持久化数据结构或迁移契约发生变化 |

**软件版本**统一采用 `X.Y.Z_BUILD` 格式。产品、固件、更新器和 SDK/API 均可采用该格式，不再为包修订号单独设置版本维度。

其中：
- `X`（MAJOR）：发生不向后兼容的重大变更。
- `Y`（MINOR）：以向后兼容方式增加功能。
- `Z`（PATCH）：向后兼容的问题修复。
- `BUILD`：构建编号，由构建流水线生成并递增，用于区分同一 X.Y.Z 下的不同构建。

例如：`2.4.1_1024` 表示软件版本为 2.4.1，构建编号为 1024。

构建编号应由自动化构建系统统一生成，避免人工指定或重复使用。具体编号生成和分配规则由工程构建系统确定。

## 3. 版本标识与发布渠道

版本字符串只表达软件版本和构建编号，不使用 `alpha`、`beta`、`rc` 等预发布标识。

开发版、测试版、正式版等发布阶段及可用范围，由 MosAPI 后台的发布渠道/版本管理机制控制，不通过在软件版本号中增加特殊字符串表达。

发布渠道与软件版本是两个独立维度：
- 软件版本回答“这是哪个版本、哪个构建”。
- 发布渠道回答“该版本面向哪个发布阶段或用户范围”。

## 4. 构建信息与追溯

构建编号是软件版本的一部分。除此之外，每个可分发构建仍必须记录以下构建元数据，以便定位问题和追溯来源：
- 产品/组件标识；
- 完整软件版本（`X.Y.Z_BUILD`）；
- 源代码 Commit SHA；
- UTC 构建时间；
- 目标 OS/平台及 CPU 架构；
- 构建配置（Release/Debug 及相关功能配置）；
- 依赖锁定文件或依赖快照身份（适用时）；
- 制品 SHA-256 摘要及签名信息（发布制品）。

构建元数据用于追溯，不额外形成另一套对用户展示的版本号。相同版本字符串不得对应不同内容的正式发布制品；如果重新构建产生不同内容，应分配新的 BUILD 编号。

## 5. 协议版本与数据版本

协议版本和数据/Schema 版本不必与软件版本同步变化，应根据各自契约的演进独立维护。

项目必须明确：
- 客户端与服务端支持的协议版本范围；
- 协议字段新增、弃用和破坏性变更规则；
- 数据格式的可读版本和可写版本；
- 历史数据迁移规则及失败处理方式；
- 未知字段和未知扩展的保留策略。

对于可选协议能力，应该优先采用能力协商，而不是只依赖客户端软件版本字符串。

## 6. 版本兼容策略

每个产品必须定义兼容策略，说明：
- 支持的历史软件版本窗口；
- 最低允许升级来源版本；
- 是否支持跨版本跳跃升级；
- 协议兼容范围；
- 数据迁移行为；
- 回滚限制；
- 停止支持策略；
- 对未知或不支持版本的处理方式。

新版本应该读取支持范围内的历史数据。在安全可行时，必须保留未知字段和扩展；否则必须阻止可能造成破坏的写入。不得静默重新解释不支持的语义。

## 7. 版本信息的唯一来源

产品仓库必须定义唯一权威版本源，或确定性版本生成流程。软件版本、构建编号应由构建系统生成或注入；安装包元数据、UI 展示、更新 Manifest 和诊断信息必须从该来源生成，不能手工维护多个副本。

正式发布 Tag 必须指向实际发布所使用的精确源代码修订。已发布 Tag 不得移动或重复使用。

## 8. 发布元数据

发布元数据应该包含：
- 产品/组件标识；
- 完整软件版本及构建编号；
- 发布渠道（由 MosAPI 后台或对应发布管理系统维护）；
- 目标平台、架构和最低 OS 版本；
- 协议/Schema 兼容声明；
- 制品 URL、大小和 SHA-256 摘要；
- 签名信息；
- 发布说明和发布时间。

Manifest 契约见 SF-04。

## 9. 弃用与停止支持

移除公共契约前必须：
1. 识别受影响的消费者和数据；
2. 发布弃用通知；
3. 定义迁移方案或替代方案；
4. 明确最早移除的版本；
5. 验证受支持的升级路径。

安全紧急情况可以加速弃用，但必须记录影响和缓解措施。

## 10. 验收清单

- [ ] 软件版本统一采用 `X.Y.Z_BUILD` 格式。
- [ ] BUILD 编号由构建系统生成并递增。
- [ ] 不使用 alpha/beta/rc 等特殊版本字符串；发布渠道由 MosAPI 后台管理。
- [ ] 产品、固件、更新器和 SDK/API 可以采用相同的软件版本规则。
- [ ] 协议和数据/Schema 版本独立管理。
- [ ] 构建元数据包含源代码 Commit、构建时间和目标平台。
- [ ] 兼容窗口及停止支持策略已记录。
- [ ] 发布 Tag 不可变。
