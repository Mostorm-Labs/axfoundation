# SF-06 — 日志与诊断规范

- **状态：** 提案中
- **版本：** 1.0
- **负责人：** 软件运维
- **关联规范：** SF-03、SF-05、SF-08、SF-09

## 1. 目的

让软件行为可观测、客户问题可诊断，同时保护隐私并控制运行开销。

## 2. 结构化日志事件

应用应该输出结构化日志。统一事件格式示例：

```json
{
  "timestamp": "2026-11-10T10:00:00.000Z",
  "level": "ERROR",
  "product_id": "com.example.receiver",
  "product_version": "2.4.1.1024",
  "platform": "windows",
  "module": "receiver",
  "event": "stream_connection_failed",
  "error_code": "RECEIVER-1001",
  "trace_id": "optional-correlation-id",
  "message": "Failed to establish stream",
  "context": { "transport": "local-network" }
}
```

不同语言中的字段名称和严重级别语义应该保持稳定。除公共格式外，可以同时采集平台原生日志。

## 3. 日志级别

| 级别 | 含义 |
|---|---|
| TRACE | 细粒度执行细节；生产环境默认关闭 |
| DEBUG | 面向开发和售后的诊断信息 |
| INFO | 预期内的生命周期和业务事件 |
| WARN | 可恢复的异常状态或降级行为 |
| ERROR | 操作失败，但进程可能继续运行 |
| FATAL | 严重故障，进程无法安全继续 |

不要在每一层重复记录同一个错误。应在具备有效上下文的位置记录，并通过结构化错误信息向上层传递。

### 3.1 日志与调试开关

如果产品提供文件日志、日志级别、内部调试界面、转储或抓包，应分别声明入口、默认值、作用范围和退出方式。高开销或可能扩大收集范围的诊断功能应显式开启。调试界面的显示状态独立于运行能力和授权。调试选项涉及网络监听范围时，应另行声明并遵守 [SF-09](SF-09-security-and-identity.md)。

## 4. 必要上下文

在可用时，日志应该包含产品/构建身份、模块、事件、稳定错误码、时间戳和关联/Trace ID。导出数据中的设备标识必须匿名化或最小化，除非业务确有必要且已获授权。

时间戳应该使用 UTC 和机器可读格式。计算持续时间及进程内顺序时应该使用单调时钟。

## 5. 存储与保留

每个产品必须定义：
- 日志位置和访问权限；
- 单文件大小上限和总存储预算；
- 滚动策略；
- 保留期限；
- 存储空间不足时的行为；
- 导出机制；
- 支持时的动态日志级别控制。

日志不得耗尽磁盘，也不得阻塞关键实时路径。密码、Token、私钥、个人数据和会话内容不得写入日志。

有实时采集、编解码或渲染路径的产品应该异步写日志，并限定待写入队列。队列饱和时应优先丢弃低级别日志并记录丢弃计数。日志目录不可写时，应明确报告降级，必要时转到有权限的诊断目录或平台日志通道。

## 6. 错误分类

使用稳定且带命名空间的错误码。示例：
- `COMMON-1xxx`：配置、存储、权限和通用运行时；
- `UPDATE-1xxx`：下载、验证、安装和回滚；
- `DEVICE-1xxx`：硬件发现和初始化；
- 产品领域使用各自的专属前缀。

错误码必须记录含义、是否可重试、用户影响和诊断建议。不得将同一个错误码重新用于不同故障。

## 7. 崩溃与健康状态报告

在平台能力允许时，采集：
- Crash Dump/Minidump 或 OS 崩溃报告；
- 异常信息和堆栈；
- 产品/构建身份；
- 进程运行时长和重启次数；
- 相关且不含敏感信息的运行状态。

健康检查应该区分：
- **Liveness（存活）：** 进程是否有响应；
- **Readiness（就绪）：** 是否能够提供工作能力；
- **Dependency Health（依赖健康）：** 必需服务/设备是否可用。

进程存在并不代表产品健康。

启动失败诊断应能覆盖主日志初始化之前的阶段。转储可能包含进程内存中的私密信息，应限制完整内存转储的启用范围、访问权限和保留时间。只有经过相应授权和隐私检查的转储才能进入共享诊断包。

## 8. 诊断包

在用户知情和脱敏的前提下，支持诊断包应该包含：
- 应用日志；
- 崩溃报告；
- 软件/构建/安装包版本；
- OS、架构和相关硬件摘要；
- 更新/安装历史；
- 脱敏配置；
- 与产品相关的网络诊断；
- 健康状态快照。

诊断包必须包含 Manifest，说明收集文件、时间范围和脱敏状态。收集过程不得包含凭据、个人内容或无关用户文件。上传或外部共享前应该取得用户确认。

诊断收集应使用明确的路径和文件类型白名单，保留原始文件，限制归档体积并记录被省略或截断的内容。应提供只生成本地包的预览方式。上传与反馈登记应分别记录结果，只有两者均成功时才报告完成了反馈提交。

## 9. 远程遥测

遥测采集必须明确目的、数据最小化原则、保留期限、访问控制和客户/隐私政策。诊断日志与产品分析数据是不同类别，不应混为一谈。

## 10. 验收清单

- [ ] 存在结构化日志和稳定错误码。
- [ ] 配置了滚动、大小和保留限制。
- [ ] 日志、内部诊断开关和收集范围有独立定义。
- [ ] 敏感信息经过脱敏。
- [ ] 已定义崩溃与健康检查策略。
- [ ] 诊断包具备实用性并通过隐私审查。
- [ ] 诊断包具有白名单、大小限制和本地预览能力。
- [ ] 售后能够通过诊断信息识别准确的产品/构建版本。
